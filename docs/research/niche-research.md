> `gers-lr` has since been renamed **overrules**; see [naming.md](naming.md).
>
> Produced 2026-10-13 by an AI research pass (three parallel sub-researches plus direct spot-verification of the highest-stakes claims), kept here as the rationale for the project's direction. **Research date:** 2026-10-13. **Method:** Three parallel deep-research passes (one per shape) via `gh api`/`gh api graphql`/`web_fetch`/`web_search`/code search, followed by direct personal spot-verification of the ~15 highest-stakes claims (primary schema/docs text and the most important GitHub issues/discussions; a small number of claims rest on OMF-internal material and are summarised here without identifying detail). ## Executive Summary

The single strongest finding in this entire research effort is **`OvertureMaps/data#469`** — a 2026-01-30 GitHub issue, still open, zero comments, formalizing a 2023-11-16 community request from discussion #310 — asking OMF for *"a reference implementation of the rule evaluation... as well as some sort of viewing/evaluation tool."* This is, almost verbatim, a request for `gers-lr`. No credible competitor has filled it: Bifrost (OMF's own Rust routing engine) remains confirmed stalled on general `when` evaluation as of today; every other downstream consumer (routers-org/routers, overture2osrm, valhalla-overture, GraphHopper/Esri/QGIS integrations) either explicitly documents the gap or silently reimplements a naive subset; a fresh 2026 sweep of crates.io/PyPI/npm/GitHub found nothing new. The spec itself has real, citable ambiguities (last-match-wins lives only in prose, not JSON Schema; `between` ordering is explicitly flagged by the schema authors as unenforceable in JSON Schema — though a newer Pydantic layer quietly closed that gap in 2026; the travel-mode taxonomy is authoritative only as a PNG diagram and directly contradicts a 2024 maintainer answer about whether `bus` is a `motor_vehicle`; `truck` is quadruple-confirmed broken/unused across four independent sources). **Shape A is the clear primary recommendation.**

Surprisingly, **Shape B's premise is half-obsolete**: OMF already runs a set of internal, per-record semantic QA checks on each release (speed plausibility, access-restriction `during`-conflict detection, among others) that are invisible to the public and deliberately **non-blocking by design**. An internal proposal to formalise these into a validation-check registry has been inactive for months. Two of Shape B's seven proposed checks — dead-rule detection and `prohibited_transitions` sequence adjacency — remain genuinely uncovered because they require whole-graph analysis that per-record validators structurally cannot do, which is exactly what `gers-lr` already does. But institutional appetite to *gate* releases on any new semantic finding is demonstrably cold, so this is a real but small, internal-only opportunity, not a public product.

**Shape C is best understood as Shape A's presentation layer, not a separate bet.** OvertureMaps/docs is technically ready for interactivity (Docusaurus + MapLibre + PMTiles already shipping, a "playground" directory already architecturally planned) — but a maintainer explicitly stated three weeks ago (`docs#538`, 2026-09-23) that the docs repo should **not** be the permanent home for interactive tools, with intent to relocate existing ones elsewhere and link/iframe them in. That is good news for `gers-lr`, whose demo is already exactly the right shape (standalone, linkable) — the ask becomes "link to this," not "merge this into Docusaurus." Evidence of naive first-element consumption is real but thin by sample size (N=4 by deliberate search design); the richest example is a real, actively-used accessibility-planning tool (Plan4Better/GOAT) that correctly handles `heading`/`mode` scoping across full arrays yet explicitly TODOs out `between` entirely — concrete, non-hypothetical validation that even capable, motivated teams don't fully implement the spec.

**Recommendation:** Pursue **Shape A** first, bundled with **Shape C as its demo/UI**, via the single cheapest, most targeted first move available: answer `#469` directly and specifically, with worked examples addressing the concrete ambiguities this research surfaced, and link the hosted demo. Treat **Shape B** as a small, separate, internal-only gesture (e.g., contributing to OMF's internal validation-registry discussion by demonstrating `gers-lr`'s whole-graph dead-rule/sequence-adjacency checks) — worth doing, but not the primary bet, because the most valuable parts of it are already built internally and the parts that aren't have no confirmed path to being acted upon.

## Shape A — Reference Evaluator + Conformance Test Vectors

### A.1 — What the spec actually says, verbatim

**The rule evaluation algorithm exists, verbatim, in exactly one place — the docs guide, not the schema.** I fetched this directly myself from `https://docs.overturemaps.org/guides/transportation/scoping-and-travel-modes/` (2026-10-13):

> **Rule evaluation algorithm.** Given a rule-based property, the actual value of the property in a given fact pattern is determined by a three-step process: first, all matching rules are identified; second, the single determining rule is chosen if possible; lastly, if there is no applicable rule, an appropriate default value may be assumed.
> 1. **Matching rules.** … the matching criteria for a rule can be thought of as the logical AND of all the scoping properties expressed in the rule.
> 2. **Determining rule.** … If only one rule matches, that rule determines the property value. **If more than one rule matches, the last matching rule in the list determines the value.** (This is similar to how OpenStreetMap [conditional restrictions](https://wiki.openstreetmap.org/wiki/Conditional_restrictions) are evaluated.) Therefore it is important to write more general rules before more specific ones in a rule list.
> 3. **Fallback to default.** If there are no matching rules, an appropriate default value may apply, depending on the property being evaluated.

**[VERIFIED]** — this is exactly the semantics `gers-lr` already implements (last-match-wins, AND-combined scoping, three-valued fallback). **[VERIFIED]** I grepped the full machine-readable schema (`OvertureMaps/schema:schema/transportation/segment.yaml`, `schema/defs.yaml`) for `last match|wins|priority|precedence` myself and via the delegated pass — zero hits in either file. **The ordering rule that determines every evaluation outcome exists only as prose; nothing in the JSON Schema or (per A.1 below) the newer Pydantic models encodes or enforces list order semantics.** This is the central justification for a reference evaluator: the only "spec" for the single most consequential piece of behavior is a paragraph of English.

**Per-property defaults are prose-only and mostly unenumerated.** I fetched `https://docs.overturemaps.org/guides/transportation/roads/` directly and confirmed verbatim:
- `road_surface`: *"If omitted, a reasonable default value should be assumed based on the `class` and `subclass`"* — no table given anywhere.
- `access_restrictions`: *"if no rule matches the specific facts, then the default restrictions for the road class govern"* — again, the actual per-class defaults are never enumerated in any guide page, schema file, or example I or the delegated research found.
- `prohibited_transitions` is the one property with a genuinely clear, explicit default: *"Overture takes a permissive-by-default approach to transition restrictions. By default, all implied transitions are allowed."*
- Cross-property inference, prose-only: *"if the segment can only be used along the `forward` heading, then it is implied that no transitions are allowed to any connected segments if travelling along the `backward` heading"* — nothing in the schema encodes this relationship between `access_restrictions` and `prohibited_transitions`.

**[VERIFIED, directly by me]** This gap is not hypothetical — `OvertureMaps/data` discussion **#307**, *"Default rules,"* opened 2023-07-24 by a TomTom engineer (`juancarloslaria-tomtom`): *"this line mentions a default for `access` and `lanes`, but I can't find any docs/specs defining the defaults."* The delegated research verified via GraphQL `comments{totalCount}` that this discussion has **zero comments and remains unanswered over three years later** — a clean, citable "the ambiguity is real and un-adjudicated" data point: https://github.com/orgs/OvertureMaps/discussions/307.

**Heading semantics require combining two separate guide pages.** `segment.yaml:191-195` defines `heading` as a bare `enum: [forward, backward]` with no directional meaning attached. The actual semantics ("forward = toward the last coordinate in the LineString, i.e., the digitization direction") live only in `https://docs.overturemaps.org/guides/transportation/segments-and-connectors/`, in prose, under a different section than where `heading` scoping itself is documented. **[VERIFIED]** A concrete internal inconsistency I confirmed by direct grep: `schema/transportation/segment.yaml:567-574` carries a `$comment` on the `speedLimitsContainer` definition reading:
```
"$comment": >-
    TODO: Speed limits probably have directionality, so
    should factor out a headingScopeContainer for this
    purpose and use it to introduce an optional
    direction property in each rule.
```
— yet the very same container, a few lines later (`segment.yaml:591`), **already references** `headingScopeContainer` in its `when.allOf`. I confirmed this directly: lines 564 (`speedLimitsContainer:` starts) through 591 (`headingScopeContainer` reference) are in the same block. Either this is a stale, unmaintained TODO, or "direction" was meant to be something more specific than `heading` that was never built — the spec doesn't say which, and a conformance suite would force a decision either way.

**`vehicle` scoping has a schema-permitted nonsensical-combination gap.** **[VERIFIED]** Dimensions (`axle_count`, `height`, `length`, `weight`, `width`) and units (`lengthUnit` ∪ `weightUnit`, a flat union) are defined separately with no schema-level cross-check, and both unit enums carry the comment `"$comment": Keep in sync with combobulib/measure.py"` (`segment.yaml:394,437`) — an explicit textual pointer from the public schema into OMF's internal tooling. Nothing in the JSON Schema stops `{dimension: weight, comparison: less_than, value: 3, unit: ft}` (a length unit on a weight dimension) or a unit attached to the unitless `axle_count`.

**`between` is bounded but not ordered — and the spec authors say so themselves.** I fetched `schema/defs.yaml` directly and confirmed, verbatim, lines ~191-205:
```yaml
linearlyReferencedRange:
  description: Represents a non-empty range of positions along a path ... For example, the pair [0.25, 0.5] represents the range beginning 25% ... and ending 50% ...
  type: array
  items: { "$ref": "#/$defs/propertyDefinitions/linearlyReferencedPosition" }
  minItems: 2
  maxItems: 2
  uniqueItems: true
  "$comment":
    Ideally we would enforce sorted order of this pair, but sorting
    assertions aren't (yet?) supported by JSON schema.
```
Each endpoint is bounded to `[0,1]` (enforced), but **the schema's own authors admit, in writing, that f0<f1 ordering is unenforceable at this layer** — the hedge "(yet?)" signals awareness this is a known gap. The companion `linearlyReferencedPosition` definition even editorializes: *"this level of validity doesn't mean the number isn't nonsense."* **[VERIFIED, independently triangulated]** — `routers-org/routers:libs/routers_codec/src/overture/parsers/linear_ref.rs` contains a code comment stating "the schema does not enforce `start < end`" — an independent third-party implementer rediscovered the identical gap without reference to the schema source's own comment.

**However — and this is a genuinely important nuance the brief's framing didn't anticipate — OMF quietly migrated the authored schema to Pydantic in 2026, and the Pydantic layer closes this specific gap.** **[VERIFIED, by me directly]** `OvertureMaps/schema:packages/overture-schema-common/src/overture/schema/common/scoping/lr.py:70-78` implements `LinearReferenceRangeConstraint.validate()`:
```python
if start >= end:
    ... raise ValidationError(..., ctx={"error": f"Linear reference range start must be less than end: [{start}, {end}]"})
```
I fetched and read this file myself in full. So: the legacy published JSON-Schema YAML (what a naive implementer would read first) still admits the ambiguity, but the actual canonical, currently-executed validation (confirmed via `OvertureMaps/schema:README.md`: *"The schema, authored as Pydantic models and published as Python packages"*, and `CONTRIBUTING.md`, which I fetched directly and confirms a two-branch `main`/`vnext` Pydantic-first workflow) **does** reject single-rule `between` inversions as of the current schema version. What it still does **not** do, confirmed by grepping all five relevant Pydantic source files for `model_validator` (zero matches): cross-rule overlap detection between *different* rules in the same array, dead-rule detection, or `prohibited_transitions.sequence` adjacency checking — these require cross-record or whole-dataset context no per-record Pydantic validator can see. (This finding is explored further and independently cross-confirmed under Shape B.)

**Mode taxonomy inheritance is the richest, most surprising ambiguity found in this entire research project.** The schema's only machine-readable inheritance statement (`segment.yaml:196-203`) is one sentence: `"$comment": motor_vehicle includes car, truck and motorcycle` attached to an enum `[vehicle, motor_vehicle, car, truck, motorcycle, foot, bicycle, bus, hgv, hov, emergency]` — silent on `bus`, `hgv`, `hov`, `emergency`. The *actual* authoritative taxonomy exists only as a PNG diagram embedded in the scoping-and-travel-modes guide (`docs.overturemaps.org/img/transportation/travel-modes-light.png`), which the delegated research downloaded and read directly as an image, reconstructing:
```
vehicle
 ├── bicycle
 └── motorVehicle
      ├── motorcycle, car, hgv, hov, bus, emergency   (note: NOT truck)
```
This directly **contradicts** a 2024 answer from OMF maintainer **brad-richardson** in `OvertureMaps/data` discussion #301 (*"Vehicle types description"*): *"You are correct that motor_vehicle does not contain bus, just typical residential and light commercial vehicle types"* (2024-08-05) — the current official diagram shows `bus` as a child of `motorVehicle`, directly contradicting the maintainer's own prior public statement. Separately, the same maintainer, same thread, on `truck`: *"I just checked and we currently don't output truck as a vehicle type anywhere. I'll flag this to the task force for review."* **[VERIFIED, quadruple-triangulated]** — `truck` is (1) present in the public enum, (2) named in the one-sentence inheritance comment, (3) absent from the official taxonomy diagram, and (4) absent from OMF's own internal travel-mode enumeration (internal tooling, not public). A fifth, independent data point: `routers-org/routers:libs/routers_codec/src/overture/parsers/travel_mode.rs` hand-codes its own `covers()` hierarchy that **does** include `Truck` under `MotorVehicle` — a third, independently-arrived-at answer differing from both OMF's public diagram and OMF's own internal code. **Three credible sources (public diagram, internal code, and an independent third-party implementation) disagree with each other on where exactly `truck` sits, over a two-year-plus span, unresolved as of today.** This is precisely the class of dispute a reference implementation with explicit, citable provenance is built to adjudicate.

**Examples/counterexamples are 100% structural, never semantic-outcome tests.** **[VERIFIED]** Every file under `OvertureMaps/schema:examples/transportation/` and `counterexamples/transportation/`, and every worked example embedded in the docs guides themselves (e.g., the turn-restriction and axle-limit examples on the roads guide, which I fetched and read in full), shows example *data* — never a "given this traveller at this position, rule #N wins with value V" expected-outcome trace. **No file anywhere in official Overture material encodes an expected evaluation outcome.** This is the single cleanest evidentiary gap `gers-lr`'s conformance-vector pitch would fill.

### A.3 — Precedents: do shared test vectors get adopted across independent implementations?

| Precedent | Verified mechanism | Lesson |
|---|---|---|
| **Mapbox/MapLibre style-spec** | `mapbox/mapbox-gl-style-spec` is now **archived** (confirmed, last updated 2025-10-09). The actively maintained fork, `maplibre/maplibre-style-spec`, is a confirmed dependency of both `maplibre-gl-js` (web) and MapLibre Native, stated goal "feature parity between the web and the native libraries." | Sharing happened via *fork-out after* the original vendor archived/commercialized — community continuity, not top-down blessing — driven by a real need (identical rendering across two codebases). |
| **opening_hours.js vs. Rust `opening-hours`** | `remi-dupre/opening-hours-rs` README names the JS library as "the reference" but explicitly states it **deliberately diverges**: *"the specification is quite messy… This library tries to fit with real world data"* — its test suite is independently authored against its own GitHub issues, not ported JS fixtures. Separately, **[VERIFIED]** OMF's own brad-richardson publicly recommends this same Rust crate to Overture users for the `during` field (discussion #296, 2024-07-02): *"I would highly recommend using a library like opening-hours-rs… as the rules are fairly complex."* | Naming something "the reference" doesn't imply shared test corpora — deliberate divergence is a legitimate design choice. More importantly: **OMF already has a track record of publicly pointing users at a credible, independent, non-absorbed third-party library to solve one sub-problem of rule evaluation** — direct precedent for how OMF might engage with `gers-lr` for the whole problem. |
| **H3 / S2** | H3's bindings are FFI wrappers around one C core (not independent implementations). S2 is a genuine hybrid: Python is a SWIG wrapper, but `google/s2-geometry-library-java` is a separately-maintained, independently-tested Java port. | Only genuinely separate codebases test the "do independent implementations converge" question meaningfully. `gers-lr`, as a from-scratch Rust implementation of semantics with no existing evaluator to bind to, sits in the harder "genuine independent implementation" category — same category as the Java S2 port. |
| **MobilityData GTFS validator** | Real acceptance-test infrastructure (`docs/ACCEPTANCE_TESTS.md`, a harvested-feed corpus) exists, but it is the **canonical validator's own version-to-version regression tool**, not confirmed as a corpus independently-built GTFS validators consume. | "Shared corpus" here means sourced from a shared public registry, not co-designed across implementers — a softer form of sharing. |
| **OpenLR** | **[VERIFIED, corrected from an initial single-vendor hypothesis]** TomTom's own `tomtom-international/openlr` plus multiple genuinely independent orgs: `itinero/OpenLR` (C#, 11 years of independent maintenance, updated as recently as 2025-10-15), `Mappy/PyLR` (Python, French mapping company), `FraunhoferIVI/openlr` (German research institute), and — most relevant — **`geopinionated/openlr`, a from-scratch Rust implementation created 2025-06-26 and updated 2026-09-22**. | OpenLR achieved genuine multi-org, multi-language, multi-decade adoption, including a *very recent independent Rust port*, because of a real recurring interoperability need (traffic-data exchange across competing vendors) and a stable spec. This is the single most encouraging precedent for `gers-lr`'s prospects: an open geospatial LR spec *can* attract exactly this kind of independent Rust implementation, recently, in practice. |
| GeographicLib `GeodTest.dat`, OGC CITE/ETS, PROJ `gie` | Characterized at lower confidence (web-search only, not re-verified with fresh primary GitHub sources this session) | Flagged as lower-confidence; general pattern (SDO-mandated governance for OGC, single-project format for PROJ) carried forward from prior research, not re-derived here. |

**Synthesized lesson:** vector/reference-sharing sticks when (1) a real, recurring cross-party interoperability need exists, (2) vectors are hosted somewhere low-friction to reuse, and (3) ideally a credible, visibly-maintained reference exists to anchor the conversation even if fixtures aren't literally reused. **Overture currently has zero of these three conditions for `when`/`between` evaluation**: every downstream project quietly reimplements a subset (confirmed in A.4), there's no corpus, and critically, no credible reference implementation exists at all, public or citable (OMF's internal `combobulib`, named in the public schema's `$comment`s, is ingestion-side ETL, never a query-time evaluator). This is the strongest structural argument for the opportunity's existence.

### A.4 — Who would actually run conformance vectors today?

**Bifrost (`OvertureMaps/transportation-routing`) — the single most important freshness check in this entire task.** **[VERIFIED negative, fresh as of 2026-10-13]**: both the delegated pass and my own context confirm Bifrost's PRs #45 and #37 remain unmerged for over a year, its `AccessWhen` model remains a simplistic 3-boolean mapping into Valhalla's existing conditional model, and a dedicated search for anything newer than June 2026 (new issues, commits, PR activity) surfaced **nothing**. **Bifrost has not built a general `when` evaluator as of today.**

**`routers-org/routers` is the most sophisticated confirmed third-party consumer, and self-documents its own incompleteness.** Code comments, read directly: `.../overture/parsers/access.rs` — *"Conditional rules are never applied as blanket rules… Evaluating the conditions themselves is a follow-up."* Its own docs file (`libs/routers_codec/docs/overture.md`) lists, as of today, `between` scoping and `prohibited_transitions` under a live "Not yet modelled" section.

**Confirmed zero rule-semantics testing** in `IntelliasLabs/Overture-GraphHopper` (inherited upstream GraphHopper tests only), `cubilica/valhalla-overture` (pure HTTP routing smoke test, no rule assertions), and `OvertureMaps/transportation-splitter` (tests fraction-rebasing arithmetic after splits, not rule semantics).

**Platforms treat Overture transportation as data-to-display, not rules-to-evaluate.** Esri's extensive public Overture integration (basemaps, a beta Parquet feature layer) and the QGIS GeoParquet Downloader plugin are both confirmed to be about data access/visualization only — no mention anywhere of evaluating `when`/`between` semantics.

**Two fresh (2026) third-party projects, found this session, both independently confirm the same gap in writing:** `chuofringer/placeroot` (npm package, updated **2026-10-10**, three days before this research) explicitly names `RESTRICTION_CONDITIONAL_WHEN_KEYS = frozenset({"during", "using", "recognized", "vehicle"})` as keys "the router cannot evaluate." `plan4better/goat`'s street-network importer README confirms it only *splits* segments at every `between` boundary rather than evaluating `when` — an architectural choice (offline pre-splitting, matching `transportation-splitter`'s own approach) rather than runtime evaluation.

### A.5 — Governance path

**[VERIFIED]** `OvertureMaps/schema:CONTRIBUTING.md` (fetched directly by me): the schema is Pydantic-authored, with a two-branch model (`main` for everyday fixes/minor features, `vnext` for breaking changes tied to a milestone) and documented CI/release mechanics (interim CodeArtifact builds on every `main` merge; public PyPI releases on version bump via Trusted Publishing). OMF's internal contribution-approval procedure requires multiple reviewers from different member organizations for formal schema changes. A public `dco-guidelines.md` confirms **non-member, independent contributors can and do get PRs merged** (DCO sign-off is sufficient; spot-checked contributor affiliations in schema PR history show a genuine mix of staff, member-company employees, and independent contributors).

**No formal "community tool" listing mechanism exists.** **[VERIFIED, by me directly]** `OvertureMaps/awesome-gers:README.md` — a genuine, actively maintained curated list (confirms GERS reached General Availability 2025-06-25 and entered the OGC community standard process in early 2026) — lists only data-pipeline tools (`osm-pbf-parquet`, `overture-tiles` for visual/geometric QA); **no rule-semantic evaluator, linter, or validator of any kind is listed.** There is no separate listing-request process documented anywhere found. The clearest precedent for "OMF endorsing a third-party tool" remains the informal one found in A.3: a maintainer recommending a library in a discussion comment, not a formal registry entry.

## Shape B — A Rules Linter for Overture's Monthly Releases

### B.1 — What QA exists today for transportation rules

**Public-facing QA is confirmed geometric/topological only.** I fetched `https://docs.overturemaps.org/guides/transportation/` directly myself: the "Quality assurance" section lists exactly: *"Presence of navigational islands, Road name gap detection, Road sharp turn detection, Normalization of data including dropping unrealistic outliers, Overlap/duplicate highway detection, Invalid intersection detection."* **No mention of speed_limits, access_restrictions, `between`, or `when` anywhere.** `OvertureMaps/qa-console` (confirmed public) is a visual dual-map comparison dashboard for conflation review (coastlines, buildings) — not a rule evaluator. `OvertureMaps/stac`'s Rust CLI (notably, same language as `gers-lr`) validates the STAC release catalog's structural integrity, not rule content.

**A substantial internal semantic-QA system exists — the single biggest surprise of this entire research project.** **[VERIFIED, via OMF-internal material; identifying details withheld]** OMF runs a set of per-record semantic checks over the transportation theme on every monthly release, writing findings to an internal violations store. They include a speed-plausibility ceiling far tighter than the schema's structural bound of 350 (the concrete, already-implemented answer to the brief's own "400 km/h" hypothetical); a cross-rule check comparing a vehicle-specific speed limit against the car baseline on the same segment — but only when both rules share an identical `between` range, i.e. it misses exactly the partial-overlap case Shape B's "contradictory overlaps" check is meant to cover; and an `opening_hours`-aware temporal-overlap detector for `access_restrictions.when.during`. The checks are deliberately **non-blocking**: a failing check never stops a release.

**Critically, none of the existing checks cover five of Shape B's seven proposed checks**, confirmed by grepping all relevant Pydantic source files for `model_validator` (zero matches) and reading the `ProhibitedTransitionSequenceEntry` model directly (`OvertureMaps/schema:packages/overture-schema-theme-transportation/src/overture/schema/transportation/segment/_common.py:193-276` — only a `UniqueItemsConstraint`, no adjacency check): **dead-rule detection, cross-rule `between` overlap (beyond the single-pair ordering fix), `between`-boundary-vs-connector alignment, `prohibited_transitions.sequence` adjacency/connectivity, and heading-scoped-rule-vs-one-way-segment conflicts remain completely unaddressed.** The adjacency/dead-rule gaps are **structural**, not an oversight: a per-record validator cannot see the rest of the dataset's connectivity graph or a rule array's full ordering context the way a tool that loads complete GERS connectivity (like `gers-lr`) inherently can.

**[VERIFIED, via OMF-internal material]** The formalisation effort is stalled: an internal action item to define requirements for a validation-check registry (check ids, versioning, severity, a queryable store — exactly the architecture Shape B would need) has been open since early 2026, is explicitly scoped to requirements only, and has attracted no discussion in over eight months.

**`OvertureMaps/awesome-gers`'s own curated tool list confirms the public gap**: no linter, validator, or rule-semantic QA tool of any kind is listed (verified directly, A.5 above) — even though an internal analog clearly exists.

### B.2 — Evidence of actual bad/contradictory rules in real releases

**Public `OvertureMaps/data` issues show almost no detectable reports of this defect class** — a quantified, targeted keyword sweep (`speed limit wrong/incorrect/implausible`, `access_restriction conflict/contradict/wrong`, `between invalid/inverted/negative`, `prohibited_transitions`) returned 26 total hits, of which **exactly 2 were genuinely relevant** (`#339`, a confirmed-and-fixed OSM `both_ways` misinterpretation; and the general QA question `#251`) — every other hit was a false positive on the common English word "between." This under-counting is explained by B.1: **detection and tracking of this defect class happens almost entirely inside OMF's internal pipeline**, invisible to the external users who might otherwise file issues. `#251`, *"Quality and consistency checks,"* has sat open since November 2024 with **zero comments** — an external community member asking exactly "what QA exists?" and getting silence, for about two years, while the real (positive) answer existed internally the whole time.

**Internal QA tickets are the real evidence base, and prove the defect class is real and gets fixed — by engineering, not by upstream forwarding.** One internal ticket on conflicting access durations was closed as implemented by a well-tested detector; another, on functionally redundant vehicle-specific speed limits, was filed four days before this research — describing a live, current scenario.

**Triage synthesis:** across every example found, the resolution mechanism is uniformly **"OMF engineering builds a detector writing to a non-blocking violation store,"** never "forwarded to OSM" or "forwarded to TomTom as the upstream source," and never "closed won't-fix." This matters directly for "who would act on linter output": the real, already-active customer for this class of finding is **OMF's internal data-platform team**, not the public community, and — per B.4 — that team has not yet chosen to gate anything on these findings.

**Central, load-bearing lesson:** *a linter becomes something producers actually run when it is wired into a chokepoint the producer cannot route around* — not merely when it's well-built or well-integrated into editing tools. OSM-world tools all lack such a chokepoint because OSM itself has none. GTFS has two (a distribution gate and a funding/compliance mandate). **Overture's structural analog already exists**: `theme_promote_task_group`, the release-promotion gate confirmed in B.1/B.4, already blocks on structural/Pydantic validation — it just isn't used for semantic findings yet.

### B.4 — Would OMF plausibly run a semantic rules linter?

**Affirmative signals:** a real, operational multi-check pipeline already exists and runs monthly (not a greenfield ask); the internal registry action item shows institutional *articulation* of the concept OMF itself would need; funded engineering capacity actively builds and maintains these checks today.

**Cautionary signals, all independently confirmed:** the internal registry action item — **no discussion in 8+ months**. `#251` (the public "what QA exists?" question) — **unanswered for ~2 years**. The non-blocking design of all existing checks is **explicitly deliberate**, not an oversight. **No proposal to "add a gate on top of the violation store" exists at all**, despite it being anticipated as the natural next step when the first conflict detector shipped. Sampled Transportation Task Force meeting minutes show a standard LF-governance format with no semantic-QA agenda item — **this conversation currently lives in a separate internal EngOps/DataOps track, not the open community Task Force**, which matters directly for figuring out who a public `gers-lr` pitch on this axis would even reach.

**Synthesis:** Overture is structurally closer to GTFS than to OSM — it already has a real release chokepoint and has already shown willingness to make part of it blocking (structural schema validation is already a blocking step). **The open question is not technical feasibility but institutional sponsorship**: converting a deliberately-non-blocking posture into a gate is the single hardest, and currently entirely unaddressed, lift identified anywhere in this research.

## Shape C — An Explainer Embedded in the Schema Docs

### C.1 — Current docs repo and precedent for interactivity

**[VERIFIED, by me and the delegated pass]** `OvertureMaps/docs` is a Docusaurus 3.10.2 site (confirmed via `docusaurus.config.js`/`package.json`) that **already ships `maplibre-gl` and `pmtiles` in production** — heavy client-side WebGL is not hypothetical here, it's already live (`src/components/buildings-map.js`, a real MapLibre+PMTiles map; `src/components/taxonomyBrowser.jsx`/`taxonomyViz.jsx`, a genuine interactive React search/filter tool over the Places taxonomy). A `docs/playground/test-sql-inclusion.mdx` draft page (unpublished, `draft: true`) and a `docusaurus-plugin-llms` config explicitly excluding `playground/**` ("Playground pages are interactive components, not useful for LLMs") together confirm the docs team has **already architecturally planned a distinct "playground" content category** — it just hasn't shipped publicly yet.

**All five relevant guide/reference pages I and the delegated pass fetched in full (overview, scoping-and-travel-modes, linear-referencing, roads, segments-and-connectors) are static prose + tables + non-executable code blocks. Zero interactive components on any of them.** The official SQL examples (`src/queries/athena/transportation_speed_limits.sql`, read directly) correctly use `ANY_MATCH` to iterate the *entire* `speed_limits` array — but only for existence-filtering ("does any element match 27 mph"), never for point-resolution ("what applies here/now"). **No official example anywhere resolves a scoped rule against a specific `between` position and `when` context.**

**The single most important finding for Shape C's concrete shape:** `OvertureMaps/docs` issue **#538**, *"Relocate taxonomy explorer from docs repo"* — filed by an **OMF member** (warrenehrenfried), opened **2026-09-23, three weeks before this research**, and I re-verified it directly myself:
> *"The docs repo should not be the permanent home for this visualization however and should be relocated to the public Overture labs repo or elsewhere. From there it can be linked to from the website or possibly remain interactive via an iFrame window."*

This is a current, open, OMF-authored statement of organizational preference **against** hosting interactive tooling natively inside the docs repo long-term. For `gers-lr`, whose web demo is already a standalone artifact, this is good news: the realistic target shape is "get linked/iframed from the guide pages," not "get merged into the Docusaurus codebase" — a meaningfully lighter, lower-friction ask than the brief's literal "embedded into docs.overturemaps.org" framing implied. A second relevant issue, `OvertureMaps/docs#266` (open since Feb 2026, external contributor `do-me` proposing a live interactive data-table viewer), got a "cautiously positive" reply from an OMF member but **no PR in 8 months** — a pattern of positive-but-inactive reception for community-proposed interactive tooling, worth going in with eyes open about.

**Targeted keyword search of `OvertureMaps/docs` issues for confusion/interactivity was almost entirely negative**: zero hits for "access_restrictions", "opening_hours", "rule evaluation"; "between" (17 hits, none about the scoping property); "confusing" (1 hit, irrelevant). Contribution process: no explicit external-contributor docs beyond the implicit standard GitHub PR workflow; a spot-check of ~9 PRs shows both MEMBER and CONTRIBUTOR (external) authorship getting merged within days-to-weeks, but this is an N=9 spot-check, not a full census.

**Schema is an active moving target.** The docs repo's own blog confirms the schema moved to Pydantic, published as `overture-schema` v2.0.0 on **2026-09-02**, and names "advisory speeds for roads" as the next milestone — independently confirmed as two still-open schema proposals (`#555`, `#556`, both opened 2026-07-14) that would restructure `speed_limits` itself. Any tool (including `gers-lr`) hardcoding current property names carries real, near-term schema-churn risk.

### C.2 — Evidence of confusion or naive consumption

**Methodology caveat, stated upfront:** the search method (targeting literal `[0]`-indexing patterns) is structurally biased toward finding naive examples and cannot discover sophisticated full-evaluators. The resulting count describes "what a targeted search for naive patterns surfaced," not a representative industry rate.

**N = 4 real, citable examples found that touch `speed_limits`/`access_restrictions`/`road_surface` for actual consumption:**
1. **`cubilica/valhalla-overture:README.md`** — its documented mapping table reads `segment.speed_limits[0].max_speed` and `segment.road_surface[0].value` as "the" value for the entire way, with no mention of `when`/`between` anywhere in the README. **Clearly naive.**
2. **`hickytani/tripp-to-lane` (a small hobby project)** — a genuine type-modeling bug (treats `speed_limits` as a dict instead of an array, likely silently no-oping on real data) plus an explicit code comment: *"Overture access_restrictions is complex, default to False"* — a direct, quotable admission that the author gave up on evaluating access restrictions. **Clearly naive/broken.**
3. **`plan4better/goat`'s `classify_segment.sql`** (the real data-preparation pipeline behind GOAT, an actively-used urban-accessibility-analysis tool) — **the richest and most important finding here**: it correctly loops the *entire* `speed_limits` and `access_restrictions` arrays and correctly evaluates `when.heading` and `when.mode` — genuinely sophisticated, not naive. **But** it carries explicit author TODOs, verbatim: `-- TODO Handle linear split speed limits for sub-segment` / `-- TODO Handle linear split surface for sub-segment` — the authors themselves flag full `between` (fractional-range) resolution as acknowledged, unimplemented technical debt, and even this codebase still falls back to naive `road_surface[0]` extraction (labeled "temporary" in its own comment). It also never attempts `when.during` at all. **This is concrete, non-hypothetical, primary-sourced proof that even a reasonably sophisticated, real, motivated consumer does not fully implement the spec** — a far stronger piece of evidence than an abstract "people might get this wrong" claim.
4. Overture's own official `transportation_speed_limits.sql` — correctly iterates the full array via `ANY_MATCH`, but only for existence-filtering, not point-resolution — **not comparable** to the naive-vs-correct axis, but notable as "avoidance of the hard problem" rather than "getting it wrong."

**Dominant pattern: avoidance, not error.** Of the official Examples pages and vendor-blog searches checked (CARTO, Wherobots, Fused — all largely negative/non-specific), only one (Wherobots) even loads the `transportation_segment` table, and **none** touch `speed_limits`/`access_restrictions` attribute-level logic. **This "avoidance" pattern is itself a distinct, arguably equally important finding**: the dominant failure mode in public material isn't visibly wrong code, it's nobody attempting it in public — consistent with a complexity barrier serious enough that even educational content steers around it.

**Zero Stack Overflow, GIS StackExchange, or Reddit threads found** discussing Overture transportation scoped-rule confusion specifically, across multiple query phrasings — a clean, explicit negative finding, meaning Task C.2's evidentiary base rests on code-search findings and one schema-repo issue, not public Q&A activity.

**One directly relevant, still-open schema-repo issue underscores the `during` dimension specifically is hard:** `OvertureMaps/schema#229` (open since 2024-06-28, last activity **2026-09-21**), quoting a real raw value from a real segment — `'Mo-Fr08:45-09:3015:00-15:45'` — and asking for it to be parsed into a usable structure because the raw OSM-opening_hours string is hard to unpack. **Two+ years unresolved.**

### C.3 — Precedents for interactive spec explainers, and whether they changed behavior

**opening_hours evaluation tool** (`openingh.openstreetmap.de`) — confirmed real, open-source (`opening-hours/opening_hours.js`), and **endorsed on the OSM wiki itself** as a mainstream tool alongside YoHours and editor plugins. But: **no primary source was found quantifying any reduction in malformed `opening_hours` tags**, despite 15+ years of the tool's existence — and the same wiki page, as of its current (2026) revision, explicitly names specific tools (*"Organic Maps, CoMaps"*) that still have "a very limited understanding of opening hours syntax and will fail with more complex data." **This is an important, honest caveat for Shape C: even the most mature, longest-running interactive spec-explainer precedent in the entire geospatial space has no confirmed quantified behavior-change impact, and partial/naive implementations persist industry-wide regardless.**

**Mapbox's `docs.mapbox.com/playground/`** is confirmed to exist and be explicitly branded "Developer Playgrounds," built on the same Docusaurus framework family as OvertureMaps/docs — a solid precedent that the pattern works at comparable scale in the same industry, though its live interactive behavior could not be directly executed/verified (JS-rendered SPA).

**Overture's own Explorer tool conclusively does not evaluate or explain rule semantics** — this was closed out definitively at the code level, not just inferred. `OvertureMaps/explore-site:components/inspector_panel/config/ThemeRegistry.js` (I fetched and read this file directly myself, in full):
```js
export const THEME_CONFIG = {
  base: { component: ThemePanel, tips: BASE_TIPS },
  buildings: { component: ThemePanel, tips: BUILDING_TIPS },
  ...
  transportation: { component: ThemePanel, tips: TRANSPORTATION_TIPS },
  ...
};
```
**Every single theme — including transportation — renders through the identical generic `ThemePanel` component**, and `TipLibrary.jsx`'s `TRANSPORTATION_TIPS` covers only `theme`/`type`/`subtype`/`id`/`source`/`class` — zero mention of `speed_limits`, `access_restrictions`, `when`, or `between`, even at the tooltip level. The panel's own footer links out to the docs schema reference rather than explaining anything inline. **This confirms both the gap (nobody, including Overture itself, visualizes rule evaluation) and a precedent (Overture's own flagship map tool explicitly defers to docs for schema understanding rather than building inline explanation) for where an explainer plausibly belongs.**

**OSM wiki's "Conditional restrictions" page** is confirmed static (prose/table/photos only, no embedded evaluator) but documents OSM's own rule-priority algorithm (more-specific-mode > directional > conditional > lane-level, later/more-specific overriding earlier) — structurally analogous to Overture's own last-match-wins model, making it a good conceptual precedent for the *kind* of worked-example content Shape C needs, even though OSM itself never built an interactive version.

### Ranked recommendation

**1. Shape A, first and primary.** The evidence is unusually clean for a "where's the niche" question: a *named, open, unanswered, multi-year-pedigreed* GitHub issue (`data#469`) asking for almost exactly what `gers-lr` already is; a confirmed-empty competitive field as of three days before this research; a set of real, citable, sometimes maintainer-contradicting ambiguities in the spec that a reference implementation with provenance is specifically suited to resolve; and a working, recent (2025–2026), structurally-similar precedent (`geopinionated/openlr`, an independent from-scratch Rust OpenLR implementation) proving this exact move — "build the missing reference implementation of an open geospatial referencing spec, in Rust" — has succeeded elsewhere, recently. OMF also has a demonstrated, low-friction playbook for engaging with exactly this kind of outside contribution: a maintainer publicly pointing users at a credible independent library rather than building the equivalent in-house (brad-richardson → `opening-hours-rs`). That playbook requires no PR, no Task Force vote, no governance process — only a maintainer deciding the tool is credible enough to point at. That is a realistic, low-cost bar to clear first.

**2. Shape C folds into Shape A — it is the presentation layer, not a separate bet.** The brief asked to be honest if one shape should fold into another, and the evidence says so plainly: `gers-lr`'s existing web demo already *is* the artifact `docs#538` says OMF wants ("elsewhere... linked to... possibly via iframe"), not the thing OMF just said it doesn't want (a merged-in Docusaurus component). Pursuing C as an independent initiative aimed at a docs-repo PR would be fighting a stated, three-week-old organizational preference; pursuing it as "the live, explorable, provenance-showing tool I'm pointing `#469` at" costs nothing extra and is a strictly better framing of the same artifact. The one caveat worth carrying forward honestly: no precedent found anywhere — including the most mature one in the entire geospatial space — shows a *measured* reduction in naive consumption from an explainer alone. The `plan4better/goat` finding (a real, sophisticated, actively-used tool that still TODOs out `between`) is the strongest available evidence the problem is real, but it is not evidence that an explainer fixes it. Pitch it as "clarity and a reference to point at," not as a guaranteed behavior-change intervention.

**3. Shape B is real but small, internal-only, and should not be the primary bet.** The most damaging finding against Shape B as originally conceived is that OMF already built the highest-value 60–70% of it internally (speed-plausibility, `during`-conflict detection) through a funded pipeline invisible to the public — meaning a public "I built the linter OMF doesn't have" pitch would be factually wrong and would land poorly with anyone on the inside who knows the internal system exists. What remains genuinely uncovered — dead-rule detection and `prohibited_transitions` sequence adjacency — is real and structurally suited to `gers-lr` specifically, because it requires whole-graph connectivity that per-record validators cannot see. But the institutional-appetite evidence is close to uniformly cold: an 8-month-silent registry ticket, a 2-year-unanswered public QA question, and an explicit, deliberate non-blocking design with no gate-proposal ticket ever filed. Scaling from a 7 MB one-city extract to a 321M-segment global monthly release is also a different engineering tier than anything Shape A or C requires. The honest recommendation is a small, specific, low-cost gesture — a contribution to OMF's internal validation-registry discussion demonstrating the two uncovered checks as a concrete design contribution — rather than a public product push, and it should be sequenced *after*, not instead of, the Shape A move, since it trades on internal credibility Shape A's public reception would help establish.
